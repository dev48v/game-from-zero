GAMEFROMZERO · DAY 67

🚨 Cops and Robbers — the first pursuit game in this series, and the first whose engine is not a search at all. Sixty-six days of looking ahead from a position; here the whole game is solved backwards before a single move is played: retrograde analysis over every (cops, robber, whose turn) state, exactly how a chess endgame tablebase is built, resolving a cop-to-move state the first time any move works and a robber-to-move state only when the last escape closes. Out of that falls a verdict no search can give you — not "the cop is better here" but the robber survives forever, proved, before you touch anything. And there is a second, completely independent algorithm for the same question that never plays the game: keep deleting corners — vertices whose closed neighbourhood sits inside a neighbour's — and the graph is cop-win exactly when it collapses to one vertex. Two unrelated programs, one answer, checked here on every connected graph up to six vertices. Then the part that is measured rather than claimed: the obvious robber policy, run away from the nearest cop, is not a rough approximation of the tablebase — on one six-vertex graph it dies in every position or survives every position depending on how the vertices are numbered. Pure vanilla JavaScript, one file, offline.

A game that is over before it starts


      
The rules take one line. A cop picks a vertex. The robber, having seen where the
      cop is, picks a vertex. Then they alternate, cop first, and a move is "walk along an edge or
      stay where you are". The cop wins the moment she stands on the robber. The robber wins by
      never letting that happen — not for a long time, forever.


      
That "forever" is why this game does not fit the machinery of the previous sixty-six days.
      Minimax needs a horizon. Here the robber's win condition is an infinite play, and no depth
      limit can ever certify it: search a thousand plies deep and all you know is that the cop has
      not won yet.


      
So you solve it backwards instead


      
Every state of this game is a triple: where the cops are, where the robber is, and whose
      turn it is. For one cop on n vertices that is 2n² states — 200 on the
      Petersen graph, 72 on a six-vertex graph. Small enough to hold all of them and work backwards
      from the end, which is exactly how a chess endgame tablebase is built.


      
start:  every state where a cop stands on the robber   -> distance 0

then repeatedly, backwards:
  a COP-to-move state is won as soon as ONE of its moves reaches a won state
  a ROBBER-to-move state is won only when the LAST of its moves has been shown won


      
That asymmetry — some for the cop, all for the robber — is the whole
      solver. Implement it as a breadth-first search backwards from the captured states, with a
      counter on each robber-to-move state that ticks down as its escapes close, and every state
      resolves in non-decreasing order of capture time.


      

        
The states that are still unresolved when the queue empties are not
        "unknown" or "too deep". They are proved robber wins. That is the thing a
        forward search can never hand you, and it is why the page can shade a vertex green and mean
        it.

      


      
The second algorithm, which never plays


      
There is an entirely different way to answer the same question, and it does not know the
      rules of the game. Call u a corner if some other vertex v
      has N[u] ⊆ N[v] — everything u can reach, including u
      itself, v can reach too. Delete corners one at a time.


      
Nowakowski-Winkler / Quilliot, 1983:
  a connected reflexive graph is cop-win  IFF  deleting corners collapses it to one vertex.


      
The intuition is that a corner is a place the robber should never stand: v
      dominates it, so a cop on v covers every square the robber could run to. Remove it
      and you have a smaller graph with the same answer.


      
Two programs with nothing in common — one an exhaustive game solve, one pure graph
      surgery. The PLAY tab runs both on every connected graph on 1, 2, 3, 4 and 5 vertices on load,
      and all 26,704 connected six-vertex graphs behind a button. Disagreements: zero. That is what
      a theorem check should look like, and it is worth more than quoting the theorem.


      
What "cop number" means, and the graph that surprised me


      
If one cop cannot win, ask how many can. The cop number is the smallest
      k such that k cops, moving simultaneously, catch any robber. Trees are 1.
      Cycles longer than a triangle are 2. The Petersen graph is 3, and the solver here confirms it
      by running out of escapes across all 20,000 three-cop states.


      

        
I intended to use a grid as the friendly cop-win
        example. It is not cop-win. A grid has no corner at all — take any vertex, and no
        neighbour's closed neighbourhood contains it — so nothing dismantles and one cop can chase
        forever. The cop number of any rectangular grid is 2, and the page reports it because the
        engine computed it rather than because I remembered it.

      


      
The measurement that changed what this page says


      
I expected the obvious robber policy — move to whichever neighbour is furthest from the
      nearest cop — to be a decent approximation of the tablebase, losing a bit of ground. Two
      things came out of running it over every position a perfect robber survives:


      
    
        
  • On every connected graph up to five vertices it is perfect. 172
        robber-win graphs, 1,160 surviving positions, 0 losses.
    • 
        
  • At six vertices it loses 8.24% of them — and the failures are concentrated: 1,902
        graphs where it dies at least once.
    • 
      


      
Then the smallest counterexample explained why, and it is not what "greedy is a weak
      heuristic" would suggest. It is a square with a two-edge tail. The robber
      survives forever by circling the square. The greedy robber runs up the tail, because the far
      end of the tail is further from the cop than anywhere on the square, and gets cornered in a
      dead end.


      
But look at the moment of the decision. The robber is on the junction. Going round the
      square and going up the tail are both distance 2 from the cop. The heuristic has
      nothing to say. Something else picks — and the something else is whatever order the neighbours
      happen to be stored in.


      

        
So the page measures it. The same abstract graph under all
        720 vertex numberings: in 240 of them the greedy robber
        survives every single position, in 240 it is caught in every
        position, and in 240 it loses exactly one. Identical graph, identical policy — the vertex
        labels decide the game. The tablebase's verdict, of course, is the same in all 720.

      


      
The natural repair is to break ties by "which square has more room behind it". Measured, it
      is worse: 14.40% lost instead of 8.24%. Flipping the tie-break the other way
      gives 5.05%. None of these numbers are properties of the policy. They are properties of an
      arbitrary choice made where the policy is silent, which is a much more uncomfortable thing to
      learn about a heuristic than "it is a bit weak".


      
Two smaller things the solve settled


      
The cop's opening square never decides the game. Over 92,214 (graph,
      starting vertex) pairs on cop-win six-vertex graphs, there was not one vertex from which the
      cop fails. It only costs her time — at most 2 extra moves, measured.


      
Corner elimination is order-independent. Widely stated, easy to assume.
      Here it is 53,408 randomised dismantling runs against the greedy one, 0 mismatches.


    

  






  

    


      
🔨 How it is built


      
1. The graph is reflexive, and that is not a detail

      
const closed = [];
for (let v = 0; v < n; v++) closed.push([v].concat(adj[v]));   // N[v] INCLUDES v

      
Both players may stay put. Drop the self-loop and you are solving a different game with a
      different answer — the robber gets forced to move, parity starts to matter, and the
      dismantlability theorem stops applying to your engine. Every move list on this page comes from
      closed, never from adj.


      
2. The state index

      
// cops are an ORDERED tuple in base n; turn 0 = cops to move
const s = (copCode * n + robber) * 2 + turn;

      
Ordered rather than sorted, so three cops on ten vertices costs 20,000 states instead of
      2,200. It is 9× waste and zero bugs, which at this size is the right trade — the sorted
      encoding needs a combinatorial rank and its inverse, and both are easy to get subtly wrong.


      
3. The solver, which is nine lines of real work

      
while (qh < qt){
  const s = queue[qh++], d = dist[s];
  if (copsToMove(s)){
    for (const p of robberPredecessors(s))          // the robber came FROM here
      if (--need[p] === 0){ dist[p] = d + 1; push(p); }     // ALL escapes now closed
  } else {
    for (const p of copPredecessors(s))             // the cops came FROM here
      if (dist[p] < 0){ dist[p] = d + 1; push(p); }        // SOME move suffices
  }
}

      
Distances are counted in plies, cop moves and robber moves alike. That is
      the detail that makes a plain FIFO queue correct: if the cop's edge cost 1 and the robber's
      cost 0, states would come off the queue out of order and the "first resolution wins" rule for
      cop-to-move states would start recording the wrong capture time.

      
need[p] is initialised to closed[r].length — the robber's full
      move list including staying put. Initialise it from adj and every robber-to-move
      state resolves one escape early.


      
4. Who places first, expressed as a quantifier

      
copsWin(G)  ⟺  ∃ c₀ ∀ r₀ : dist[(c₀, r₀, cops-to-move)] ≥ 0

      
Cop picks, then the robber picks having seen her. Swap the quantifiers and every
      connected graph becomes cop-win, because the cop would simply stand on the robber. The order
      of those two symbols is the entire difficulty of the game.


      
5. The independent checker

      
// u is a CORNER if some v != u has N[u] ⊆ N[v], both closed, both restricted to
// what is still alive. Bitmasks, so the subset test is one AND.
if ((N[u] & live & ~(N[v] & live)) === 0) remove(u);

      
Written from the definition and deliberately not sharing a line of code with the solver.
      Restricting to live matters: a vertex that was not a corner at the start can
      become one after its neighbours are deleted, which is the whole reason the process works.


      
6. Chases that end without a ply cap

      
const key = encodeCops(cops, n) * n + robber;
if (seen[key]) return { captured: false, cycled: true };    // proof, not a timeout
seen[key] = 1;

      
Both policies are memoryless functions of the state, so a repeated state means the
      trajectory is periodic and the robber is never caught. Without this the study would need a
      ply budget, and every "escaped" result would carry an asterisk saying "or the budget ran
      out".


      
7. What the tests actually pin

      
// the two algorithms, on every connected graph up to 6 vertices
assert(copsWin(G,1).win === dismantle(G).ok)   for all 27,476 of them;

// the enumeration itself, against a known sequence
assert(connectedCount(n) === [1,1,4,38,728,26704][n-1]);   // OEIS A001187

// facts that would survive a broken solver only by luck
assert(copNumber(tree) === 1 && copNumber(C7) === 2 && copNumber(Petersen) === 3);
assert(copNumber(grid(4,4)) === 2);            // not 1 - grids have no corner

// the control that makes the policy race mean anything
assert(robberPolicyStudy(6, optimalRobberMove).caught === 0);

// and the headline, which is a measurement and not an assertion
relabelStudy(squareWithTail, greedy).hist === { 0: 240, 1: 240, 11: 240 };

      
The control on the third-from-last line is the one that earns the rest: if the perfect
      robber were ever caught in a position the tablebase says it survives, the harness and not the
      policy would be the story.


      
8. What this engine is not

      
// Exhaustive over the state space, so exact - and therefore bounded by it.
// One cop is O(n^2), k cops is O(n^(k+1)); ten vertices and three cops is 20,000
// states and instant, twenty vertices and four cops is 6.4M and no longer a web page.
// Cop number in general is hard; nothing here approximates it, it only enumerates.

      
Stated in the code next to the limit rather than in the copy, because it is a property of
      the implementation and not a disclaimer.
