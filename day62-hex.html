No draws: proved by exhaustion, in your browser, right now

Every other classic board game can end in a draw. Hex cannot: if you fill a Hex board completely, with any colouring at all — not just legal alternating play, but any of the 2n² assignments — then exactly one of the two connections exists. Never zero, never both. Rather than cite the theorem, this page checks it: 512 colourings on 3×3 run on page load, and all 65,536 on 4×4 run when you press the button. Each one is a fresh union-find, and each one is asserted to have red-wins xor blue-wins.

The bridge — and the measurement that changed this page

Two same-coloured stones a hop apart with exactly two empty cells between them are already connected in every way that matters: whichever carrier the opponent takes, you take the other. The obvious thing to claim next is that invading a bridge should barely move a Monte-Carlo evaluation, since nothing was actually cut. That claim was measured here and it turned out to be false — for the plain uniform-random rollout the AI above uses by default. A uniform random finish does not know what a bridge is: it scatters stones, so red keeps the link only when it happens to land on one of the two carriers first, and explicitly resolving the bridge therefore looks like a real gain.

The fix is the one real Hex programs use, and it is a single pattern: during the rollout, if the opponent plays a carrier of one of your bridges, answer on the other carrier before doing anything else. Below, the left board is a fixed 7×7 position whose only red gap is one bridge, and the right board is a ladder of four bridges running top to bottom — a connection red should essentially never lose if it answers every invasion. Press the button and both boards are evaluated under both policies with the same budget. Watch the last column: the blind policy holds the ladder about three times in four, the bridge-aware one very nearly always. Very nearly, not always — and that gap is honest too, because a single stone can land on the carriers of two different bridges at once and only one of them can be answered. Every number is computed when you click; nothing is stored in the page.

Why the first player wins — and why nobody can tell you the move

Suppose the second player had a winning strategy. The first player could then play any move at all, pretend to be the second player, and follow that strategy — and if the strategy ever asks for a cell already occupied by that extra stone, play anywhere else and carry on. An extra stone in Hex is never a liability, because stones do nothing but connect. So the first player would win too, and both players cannot win the same game — because there are no draws. Contradiction, so the second player has no winning strategy, and since somebody must have one, it is the first player.

Read that again and notice what it does not do: it never names a move. It is a proof by contradiction that produces no construction, which is why 11×11 Hex has been played for eighty years without anyone knowing the winning opening. The largest board on which the first move has been solved is far smaller than the board you are playing on above. The fix is social rather than mathematical: the pie rule. One player places a stone, and the other may either reply normally or take that stone as their own — so the opener is punished for playing anything too strong.

In code the swap is prettier than it sounds. The rhombus is symmetric under transposing (r,c) → (c,r): that map sends row 0 to column 0 and row n−1 to column n−1, and — the part worth checking — it maps the six neighbour offsets onto themselves. So transposing the board and flipping the colours gives a position that is the same game with the roles exchanged. That is exactly one line, and the page asserts the automorphism property over every cell of every board size from 3 to 11.

—

There is no path-finding on this page. A stone is placed, it is unioned with the same-coloured cells touching it and with a virtual border node if it sits on one of your two edges, and the win test is two integer comparisons. That is the whole engine, and it runs in near-constant time per move regardless of board size. Everything else — the no-draw theorem, the heuristic-free Monte-Carlo player, the bridge, the strategy-stealing argument, the pie rule — are consequences of the same two facts: Hex stones only ever connect, and a filled Hex board always has exactly one winner. Every hexagon is a real inline SVG <polygon> with six computed points; the four coloured borders are polylines built from the boundary cells' own edges, so they line up exactly. 🔨 Build it yourself

    
Hex is the game where picking the right data structure deletes the entire game engine. Refuse to write a path-finder and write a disjoint-set forest instead, bolt four fake cells onto the edges of the board, and the win test becomes an integer comparison that costs nothing. Ten blocks, in order, from an empty file — the grid, the union-find, the virtual borders, the move, the win test, the theorem, the rollout, the Monte-Carlo player, the bridge, and the hexagons.

    1
    A hex grid is a square array with six neighbour offsets
    
        
    Do not model hexagons. Model an n×n array and change what “adjacent” means. A Hex board is a rhombus of hexagons, and if you index it by row and column then each cell touches six others: the two horizontal ones, and two each in the rows above and below — but skewed, because each row is shifted half a hexagon to the right. That skew is the entire difference between a hex grid and a chessboard, and it is four lines of table. Store the whole board as a flat Uint8Array of 0, 1 and 2; a cell is an integer r * n + c and nothing else.
    
        
    const EMPTY = 0, RED = 1, BLUE = 2;

// row is shifted half a hex right of the row above it, so the six
// neighbours of (r,c) are NOT the eight of a square grid minus two
const NB = [ [-1, 0], [-1, 1], [0, -1], [0, 1], [1, -1], [1, 0] ];

function neighbours(n, idx){
  const r = (idx / n) | 0, c = idx % n, out = [];
  for (let k = 0; k < 6; k++){
    const rr = r + NB[k][0], cc = c + NB[k][1];
    if (rr >= 0 && rr < n && cc >= 0 && cc < n) out.push(rr * n + cc);
  }
  return out;
}
// degrees: 6 inside, 4 along an edge, 3 at the two obtuse corners,
// 2 at the two acute corners — worth asserting, it catches sign errors

    2
    Union-find: the whole game engine, in twelve lines
    
        
    Hex stones never move and never get captured. That single fact is why you should never write a path-finder for it: the connectivity of the board only ever grows, and the data structure for a relation that only grows is a disjoint-set forest. Each cell points at a parent; the root of the chain names the group. Two refinements make it effectively constant time: union by rank, which keeps trees shallow by hanging the shorter tree off the taller one, and path compression, which flattens every chain you walk. Together they give the inverse-Ackermann bound, which for any board you can render is indistinguishable from a single array read.
    
        
    function find(st, x){
  let r = x;
  while (st.parent[r] !== r) r = st.parent[r];
  while (st.parent[x] !== r){ const nx = st.parent[x]; st.parent[x] = r; x = nx; }
  return r;                                   // path compression on the way out
}

function union(st, a, b){
  let ra = find(st, a), rb = find(st, b);
  if (ra === rb) return false;                // already the same group
  if (st.rank[ra] < st.rank[rb]){ const t = ra; ra = rb; rb = t; }
  st.parent[rb] = ra;                         // union by rank
  if (st.rank[ra] === st.rank[rb]) st.rank[ra]++;
  return true;
}

    Four cells that do not exist
    
        
    Here is the trick that removes the last of the code. Allocate four extra slots past the end of the board and call them RED_TOP, RED_BOTTOM, BLUE_LEFT and BLUE_RIGHT. They are not squares, they are not drawn, and nobody can play on them — they exist only to be unioned. A red stone on row 0 joins RED_TOP; a blue stone in column n−1 joins BLUE_RIGHT. Now the question “does red have a chain touching both the top and the bottom?” — which sounds like a graph traversal — is the question “are these two integers equal?”. One forest holds both colours safely, because you only ever union same-coloured cells, so the red and blue trees can never touch.
    
        
    // four virtual nodes live just past the n*n real cells
const vTop   = n => n * n;
const vBot   = n => n * n + 1;
const vLeft  = n => n * n + 2;
const vRight = n => n * n + 3;

function newBoard(n){
  const N = n * n + 4;
  const st = { n, cells: new Uint8Array(n * n),
               parent: new Int32Array(N), rank: new Uint8Array(N),
               history: [], toMove: RED, swapped: false };
  for (let i = 0; i < N; i++) st.parent[i] = i;
  return st;
}

    4
    A move is at most seven unions
    
        
    Write the stone into the array, then union it with anything of the same colour it now touches: up to six neighbours, plus up to two border nodes if it sits on one of your own edges (a cell can be on both, on a 1×1 board or in a corner of your own two edges). Note what is absent — no captures, no liberties, no re-scan of the board, no incremental path repair. Placing a stone in Hex is genuinely the cheapest move in board games, and it never gets more expensive as the game fills up.
    
        
    function addStone(st, idx, colour){
  const n = st.n;
  if (idx < 0 || idx >= n * n || st.cells[idx] !== EMPTY) return false;
  st.cells[idx] = colour;
  const r = (idx / n) | 0, c = idx % n;

  if (colour === RED){                       // red owns top and bottom
    if (r === 0)     union(st, idx, vTop(n));
    if (r === n - 1) union(st, idx, vBot(n));
  } else {                                   // blue owns left and right
    if (c === 0)     union(st, idx, vLeft(n));
    if (c === n - 1) union(st, idx, vRight(n));
  }
  const nb = neighbours(n, idx);
  for (let k = 0; k < nb.length; k++)
    if (st.cells[nb[k]] === colour) union(st, idx, nb[k]);
  return true;
}

    5
    The win test, which is two comparisons
    
        
    This is the payoff for the previous three blocks. There is no queue, no visited set, no recursion and no board scan — just two find calls per colour and an equality. It is worth returning the two flags separately rather than a single winner, because that lets you assert the property that makes Hex Hex: on a full board exactly one flag is true, and on any board, full or not, the two flags are never both true, since a red chain and a blue chain would have to cross and hexagons do not permit that.
    
        
    function winnerFlags(st){
  const n = st.n;
  return {
    red:  find(st, vTop(n))  === find(st, vBot(n)),
    blue: find(st, vLeft(n)) === find(st, vRight(n))
  };
}

function winnerUF(st){
  const f = winnerFlags(st);
  return f.red ? RED : f.blue ? BLUE : EMPTY;
}
// invariant, on every position ever reachable: !(f.red && f.blue)

    Prove the no-draw theorem instead of quoting it
    
        
    The Hex theorem says a completely filled board contains exactly one winning connection. It is equivalent to the Brouwer fixed-point theorem, which is a lovely sentence to write and a useless one to trust. On a 3×3 board there are only 2⁹ = 512 complete colourings and on 4×4 only 2¹⁶ = 65,536, so enumerate them with a bitmask, build a fresh union-find for each, and assert red !== blue every single time. Two lines of loop buy you a theorem you have personally verified, and the same routine doubles as a regression test for addStone — a sign error in the neighbour table shows up instantly as a draw.
    
        
    function fullBoardFlags(n, mask){
  const st = newBoard(n);
  for (let k = 0; k < n * n; k++)
    addStone(st, k, ((mask >> k) & 1) ? BLUE : RED);
  return winnerFlags(st);
}

function proveNoDraws(n){
  const total = 1 << (n * n);
  let red = 0, blue = 0, draws = 0, both = 0;
  for (let m = 0; m < total; m++){
    const f = fullBoardFlags(n, m);
    if (f.red && f.blue) both++;
    else if (f.red) red++; else if (f.blue) blue++; else draws++;
  }
  return { total, red, blue, draws, both };   // draws and both must be 0
}

    A random rollout, and the branch you never write
    
        
    Now spend the theorem. Take the position, shuffle the empty cells, and deal them out alternately to the two players — a completely random finish with no judgement of any kind. Because the board ends up full, the theorem guarantees somebody won, so the function returns RED or BLUE and there is no third case to handle. That missing branch is the whole reason Monte-Carlo works so unreasonably well on Hex and so badly on games where a random finish usually ends in a mess that needs evaluating. Alternating the fill matters: it keeps the stone counts legal, which keeps the estimate honest.
    
        
    function rolloutWinner(st, colourToMove, rnd){
  const w0 = winnerUF(st);
  if (w0) return w0;                          // already decided
  const b = cloneBoard(st), e = emptyCells(b);
  for (let i = e.length - 1; i > 0; i--){      // Fisher–Yates
    const j = (rnd() * (i + 1)) | 0;
    const t = e[i]; e[i] = e[j]; e[j] = t;
  }
  let col = colourToMove;
  for (let i = 0; i < e.length; i++){ addStone(b, e[i], col); col = 3 - col; }
  return winnerUF(b);                         // never EMPTY — that is the theorem
}

    8
    A player with no heuristic at all
    
        
    For every empty cell: play there, run N random finishes, count how many you won. Pick the cell with the best ratio. There is no opening book, no pattern table, no notion of “centre is good” or “connect towards your edge” anywhere in this function — and yet it plays a recognisable game, because a cell that lies on many of your possible connections simply wins more random finishes. Keep the counters as running totals rather than one big batch, so the UI can add a few rollouts per frame and let you watch the estimates settle. Accumulating also means you can stop whenever you like.
    
        
    function mcInit(st, colour){
  const cands = emptyCells(st);
  return { colour, cands, wins: new Int32Array(cands.length),
           plays: new Int32Array(cands.length), total: 0 };
}

function mcRun(st, mc, per, rnd){             // add `per` rollouts to every candidate
  const other = 3 - mc.colour;
  for (let i = 0; i < mc.cands.length; i++){
    const b = cloneBoard(st);
    addStone(b, mc.cands[i], mc.colour);
    for (let t = 0; t < per; t++){
      if (rolloutWinner(b, other, rnd) === mc.colour) mc.wins[i]++;
      mc.plays[i]++; mc.total++;
    }
  }
  return mc;
}
// a move that wins outright scores exactly 1.0 for free: rolloutWinner
// short-circuits on an already-decided board, and no random fill can undo a
// completed connection

    Bridges: six offsets, two carriers, one uncuttable link
    
        
    Two stones of the same colour sitting a hop apart in one of six specific directions share exactly two empty neighbours. Those two cells are the carriers, and the pair is connected whether the opponent likes it or not: if they take one carrier you take the other, and the link survives. This is why strong Hex play looks so loose — players build with gaps because the gaps are already connections. Detection is a table lookup, not a search. Then measure what a bridge is worth to the evaluator from block 7, and you get the surprise this page is built around: nothing, because a uniform random finish does not know what a bridge is. Fix that with a single pattern in the rollout — when the opponent takes a carrier, answer on the other one — and a chain of four bridges goes from “red holds it about three times in four” to “red holds it in about 999 rollouts in 1,000”.
    
        
    // [dr, dc, carrierA, carrierB] — the six bridge directions
const BRIDGES = [
  [-2,  1, [-1, 0], [-1, 1]], [-1,  2, [-1, 1], [ 0, 1]],
  [ 1,  1, [ 0, 1], [ 1, 0]], [ 2, -1, [ 1, 0], [ 1,-1]],
  [ 1, -2, [ 1,-1], [ 0,-1]], [-1, -1, [ 0,-1], [-1, 0]]
];

function findBridges(st, colour){
  const n = st.n, out = [];
  for (let idx = 0; idx < n * n; idx++){
    if (st.cells[idx] !== colour) continue;
    const r = (idx / n) | 0, c = idx % n;
    for (const [dr, dc, p, q] of BRIDGES){
      const rr = r + dr, cc = c + dc;
      if (rr < 0 || rr >= n || cc < 0 || cc >= n) continue;
      const other = rr * n + cc;
      if (other < idx || st.cells[other] !== colour) continue;   // count once
      const k1 = (r + p[0]) * n + (c + p[1]);
      const k2 = (r + q[0]) * n + (c + q[1]);
      if (st.cells[k1] === EMPTY && st.cells[k2] === EMPTY)
        out.push({ a: idx, b: other, carriers: [k1, k2] });
    }
  }
  return out;
}
// the reply: if the opponent plays one carrier, answer on the other
const bridgeReply = (br, invaded) =>
  br.carriers[0] === invaded ? br.carriers[1]
: br.carriers[1] === invaded ? br.carriers[0] : -1;

// ...and the same idea INSIDE the rollout, which is what actually matters.
// Walk the ring of six neighbours around the cell just played, in cyclic
// order: if ring[i] and ring[i+2] are both the opponent and ring[i+1] is
// still empty, you just stepped on a carrier — ring[i+1] saves the bridge.
const RING = [[0,1],[1,0],[1,-1],[0,-1],[-1,0],[-1,1]];

function saveBridgeReplies(st, idx, colour){
  const ring = ringCells(st.n, idx), other = 3 - colour, out = [];
  for (let i = 0; i < 6; i++){
    const a = ring[i], mid = ring[(i + 1) % 6], b = ring[(i + 2) % 6];
    if (a < 0 || b < 0 || mid < 0) continue;
    if (st.cells[a] === other && st.cells[b] === other
        && st.cells[mid] === EMPTY) out.push(mid);
  }
  return out;
}
// In the rollout: pop a pending reply if there is one and it is still
// empty, otherwise take the next cell off the shuffle. Use a STACK, not a
// queue — an invasion has to be answered now, so the newest one outranks
// anything left over. Everything else stays uniformly random: this is one
// pattern, not an evaluation function.

    Drawing it: six points, two spacings, four borders
    
        
    A pointy-top hexagon of circumradius R is six points at 60° steps starting from straight up. Its width is √3 R and consecutive rows sit 1.5 R apart vertically and half a width to the right — and that half-width shift is precisely the row skew from block 1, which is how you know the picture and the array agree. Do not draw the four coloured borders as straight lines guessed by eye: build them out of the boundary cells' own edge points, so they meet the hexagons exactly. Vertex 5→0→1 of every cell in row 0 is a continuous polyline, because vertex 1 of one hexagon is vertex 5 of the next.
    
        
    function hexPoints(cx, cy, R){                 // pointy-top: 0 = top, clockwise
  const p = [];
  for (let k = 0; k < 6; k++){
    const a = (-90 + 60 * k) * Math.PI / 180;
    p.push([cx + R * Math.cos(a), cy + R * Math.sin(a)]);
  }
  return p;
}
